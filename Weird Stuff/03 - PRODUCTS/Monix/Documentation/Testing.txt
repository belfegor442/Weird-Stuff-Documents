============================================================

1. PURPOSE
   ============================================================

This document defines the testing framework for Monix.

Its purpose is to establish what must be tested, how testing is
organized, how failures are classified, and what conditions must
be considered before a release is approved.

============================================================
2. TESTING PRINCIPLES
=====================

[MANDATORY]

Testing must provide reasonable evidence that the tested
functionality behaves as intended.

[MANDATORY]

Tests must not knowingly be represented as passing when they
have actually failed or have not been executed.

[MANDATORY]

Known critical failures must be evaluated before a stable release.

[RECOMMENDED]

Tests should be deterministic and reproducible whenever practical.

============================================================
3. TEST LEVELS
==============

Monix may use the following testing levels:

* Unit Testing.
* Integration Testing.
* End-to-End Testing.
* System Testing.
* Regression Testing.
* Performance Testing.
* Security Testing.
* Rendering Testing.
* Compatibility Testing.

============================================================
4. UNIT TESTING
===============

Unit tests validate isolated components or pieces of logic.

Potential targets include:

* Parsers.
* Configuration.
* Logging.
* Data models.
* Detection logic.
* Cache logic.
* Utility functions.
* Validation logic.

[MANDATORY]

Unit tests must validate the expected behavior of the component
under normal and relevant failure conditions.

[RECOMMENDED]

New complex logic should have corresponding unit tests.

============================================================
5. INTEGRATION TESTING
======================

Integration tests validate interactions between multiple
components.

Potential combinations include:

* Monitoring + processing.
* Logging + storage.
* Configuration + runtime.
* Shader parser + compiler.
* Shader compiler + cache.
* Application + renderer.
* Security analysis + event system.

[MANDATORY]

Integration tests must verify that connected components exchange
data correctly where the interaction is important to product
functionality.

============================================================
6. END-TO-END TESTING
=====================

End-to-end tests validate complete application workflows.

Possible workflows include:

* Application startup.
* Configuration loading.
* Monitoring initialization.
* Logging.
* Shader loading.
* Rendering initialization.
* Settings changes.
* Product shutdown.

[MANDATORY]

Critical user-facing workflows must be tested before stable
release.

============================================================
7. REGRESSION TESTING
=====================

Regression testing verifies that changes have not unintentionally
broken existing functionality.

[RECOMMENDED]

Regression testing should be performed after major changes to:

* Rendering.
* Shaders.
* Monitoring.
* Logging.
* Security systems.
* Configuration.
* Update mechanisms.

============================================================
8. RENDERING TESTING
====================

Rendering tests validate the graphics pipeline.

Potential areas include:

* Vulkan initialization.
* Device selection.
* Resource creation.
* Pipeline creation.
* Shader compilation.
* Shader loading.
* Multi-pass execution.
* Feedback resources.
* Render targets.
* Resize handling.
* Shutdown.
* Recovery from failures.

[MANDATORY]

A rendering test must not be considered successful solely because
the application starts. The relevant rendering operation must
actually be validated.

============================================================
9. SHADER TESTING
=================

Shader testing may cover:

* Shader parsing.
* Preset parsing.
* Include resolution.
* Dependency resolution.
* Compilation.
* SPIR-V generation.
* Reflection.
* Pipeline creation.
* Runtime execution.
* Multi-pass execution.
* Feedback behavior.
* Cache interaction.

[MANDATORY]

Invalid shaders must produce an appropriate failure result.

[MANDATORY]

Shader compilation failures must not be reported as successful
compilation.

[RECOMMENDED]

Representative valid and invalid shader inputs should be tested.

============================================================
10. SHADER CACHE TESTING
========================

The shader cache must be tested for:

* Cache hit.
* Cache miss.
* Cache invalidation.
* Dependency changes.
* Compiler version changes.
* Corrupted entries.
* Manifest errors.
* Atomic writes.
* Eviction behavior.

[MANDATORY]

A stale cache entry must not be used when relevant source,
dependency, compiler, or compatibility information has changed.

============================================================
11. MONITORING TESTING
======================

Monitoring tests may validate:

* CPU readings.
* Memory readings.
* GPU readings.
* Temperature readings.
* Storage readings.
* Network readings.
* Process enumeration.

[MANDATORY]

Unavailable hardware data must be handled safely.

[MANDATORY]

Test results must distinguish between valid data and intentionally
simulated or unavailable data.

============================================================
12. PROCESS TESTING
===================

Process analysis may be tested using controlled test cases.

Potential areas include:

* Process discovery.
* Metadata extraction.
* Resource measurements.
* Classification.
* Reputation.
* Heuristic analysis.

[MANDATORY]

A test must verify that heuristic classifications are not
incorrectly presented as verified facts.

============================================================
13. SECURITY TESTING
====================

Security testing may cover:

* Authentication.
* Authorization.
* Access control.
* Secrets handling.
* Input validation.
* Update verification.
* Security logging.
* Privileged operations.
* Process actions.
* Configuration security.

[MANDATORY]

Security-critical functionality must be tested before a stable
release.

[MANDATORY]

Tests must not use uncontrolled real-world targets without
appropriate authorization.

============================================================
14. SCRAM TESTING
=================

SCRAM must be tested separately in TEST and REAL configurations.

TEST MODE:

[MANDATORY]

Test mode must verify SCRAM logic without intentionally
performing actions reserved for real emergency operation.

REAL MODE:

[MANDATORY]

Real-mode testing must only be performed when the relevant
environment, permissions, and consequences are appropriately
controlled.

[MANDATORY]

Testing must verify that the active mode is correctly detected
before any high-impact action.

============================================================
15. CONFIGURATION TESTING
=========================

Configuration testing may cover:

* Valid values.
* Invalid values.
* Missing values.
* Default values.
* Corrupted configuration.
* Version migration.
* Runtime changes.

[MANDATORY]

Invalid configuration must not silently produce unsafe or
undefined behavior.

============================================================
16. LOGGING TESTING
===================

Logging tests may validate:

* Event creation.
* Severity.
* Formatting.
* Timestamps.
* Source information.
* Buffer behavior.
* Rotation or persistence where applicable.
* Error handling.

[MANDATORY]

Tests must verify that sensitive credentials and secrets are not
unintentionally written to logs.

============================================================
17. SNAPSHOT TESTING
====================

Snapshot functionality may be tested for:

* Capture.
* Serialization.
* Storage.
* Loading.
* Validation.
* Corruption handling.
* Version compatibility.

[MANDATORY]

A corrupted or incompatible snapshot must not be silently treated
as valid.

============================================================
18. PERFORMANCE TESTING
=======================

Performance testing may measure:

* CPU usage.
* Memory usage.
* GPU usage.
* Startup time.
* Rendering performance.
* Shader compilation time.
* Cache performance.
* Logging performance.
* Monitoring overhead.

[RECOMMENDED]

Performance testing should use representative workloads.

[MANDATORY]

A performance optimization must not be accepted when it
knowingly introduces an unacceptable security or correctness
regression.

============================================================
19. COMPATIBILITY TESTING
=========================

Compatibility testing may include:

* Operating system versions.
* Hardware configurations.
* GPU vendors.
* Graphics drivers.
* Display configurations.
* Storage configurations.

============================================================
20. FAILURE TESTING
===================

Monix should be tested under controlled failure conditions.

Examples include:

* Missing files.
* Invalid configuration.
* Corrupted cache.
* Shader compilation failure.
* GPU initialization failure.
* Unsupported hardware.
* Missing sensor data.
* Network failure.
* Permission denial.
* Unexpected process termination.

[MANDATORY]

Expected failure conditions must be handled without falsely
reporting successful operation.

============================================================
21. TEST DATA
=============

[MANDATORY]

Test data must be appropriate for the purpose of the test.

[MANDATORY]

Production secrets and unnecessary real personal data must not
be used in testing.

[RECOMMENDED]

Synthetic or controlled test data should be preferred whenever
possible.

============================================================
22. TEST ENVIRONMENTS
=====================

Testing may be conducted in:

* Development.
* Dedicated test environments.
* Staging.
* Controlled production validation where necessary.

[MANDATORY]

Tests that could modify real user data or production systems must
not be executed without appropriate authorization and controls.

============================================================
23. TEST RESULTS
================

A test may be classified as:

PASS
Expected behavior confirmed.

FAIL
Expected behavior not confirmed.

BLOCKED
Testing could not be completed because of an external condition.

SKIPPED
Testing was intentionally not executed.

NOT APPLICABLE
The test does not apply to the tested configuration.

[MANDATORY]

A test that was not executed must not be represented as PASS.

============================================================
24. BUG SEVERITY
================

Monix may classify defects as:

CRITICAL
Severe issue affecting security, data integrity, essential
functionality, or system stability.

HIGH
Major issue with substantial functional or operational impact.

MEDIUM
Meaningful issue that does not normally prevent general use.

LOW
Minor issue with limited impact.

[MANDATORY]

Severity must reflect the actual or reasonably assessed impact.

============================================================
25. RELEASE BLOCKERS
====================

A defect may be considered a release blocker when it:

* Creates a critical security problem.
* Causes serious data corruption.
* Prevents essential functionality.
* Causes repeatable catastrophic failure.
* Breaks a mandatory release requirement.

[MANDATORY]

Known release blockers must be evaluated before a stable release.

[MANDATORY]

A release blocker must not be deliberately hidden from the
release decision process.

============================================================
26. TEST EVIDENCE
=================

[RECOMMENDED]

Important test runs should retain:

* Test name.
* Test version.
* Environment.
* Result.
* Date.
* Relevant logs.
* Failure information.
* Associated change or build.

[MANDATORY]

Evidence must not be intentionally altered to produce a false
result.

============================================================
27. CONTINUOUS TESTING
======================

[RECOMMENDED]

Automated testing should be integrated into the development
process where practical.

Potential automated stages include:

* Build validation.
* Unit tests.
* Integration tests.
* Shader tests.
* Security checks.
* Regression tests.

============================================================
28. RELEASE TEST GATE
=====================

Before a stable release:

[MANDATORY]

The release must have:

* A successful build.
* Required tests executed.
* Critical failures evaluated.
* Applicable security checks completed.
* Applicable compatibility checks completed.
* Release artifacts identified.

[MANDATORY]

Failure of a mandatory release gate must be resolved, formally
accepted by the appropriate authority, or prevent the release.
