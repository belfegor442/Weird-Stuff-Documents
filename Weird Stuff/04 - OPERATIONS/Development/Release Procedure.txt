WEIRD STUFF
RELEASE PROCEDURE

Version: 1.0
Status: IN FORCE
Effective Date: September 12, 2026
Owner: Weird Stuff
Classification: INTERNAL

1. RELEASE STATES

DEVELOPMENT -> TESTING -> RELEASE CANDIDATE -> STABLE RELEASE

A product may omit a state only when the responsible team has documented the reason and risk.

2. PRE-RELEASE

[MANDATORY]
The intended release version must be identifiable.

[MANDATORY]
Known critical defects affecting security, data integrity, or essential operation must be evaluated before release.

[MANDATORY]
Release artifacts must be generated from the intended source revision.

[RECOMMENDED]
Release notes should identify material changes, fixes, known issues, and compatibility information.

3. VALIDATION

[MANDATORY]
Required tests for the product must pass or have an explicitly accepted exception.

[MANDATORY]
Security-sensitive releases must receive appropriate security review.

4. PUBLICATION

[MANDATORY]
The published version must match the version recorded by the project.

[MANDATORY]
Stable and development artifacts must remain distinguishable.

[RECOMMENDED]
Important artifacts should be signed or integrity-verified where technically practical.

5. ROLLBACK

[MANDATORY]
Critical releases should have a recovery or rollback mechanism whenever technically practical.

6. POST-RELEASE

[RECOMMENDED]
Release health should be monitored after publication.

[MANDATORY]
Material release incidents must be documented and escalated according to the incident-response procedure.

END OF DOCUMENT
